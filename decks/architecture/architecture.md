## [diagram] The conversation gathers context for the planner
The conversation agent asks questions until it judges it has enough. Its summary and the facts it collected become the planner's input.

![The user describes their situation and the conversation agent asks up to five questions to gather context. When it judges the conversation complete, it sums up the situation and the facts collected. When the user presses Start plan, these go to the planner agent, which queries the service graph and returns a plan of steps and tasks. Both agents call Claude on Bedrock and use the service graph MCP server through AgentCore Gateway.](diagrams/journey.svg)

Notes: Each conversation turn returns the next question, the facts collected so far and a complete flag. The agent decides when it has enough; after five questions the service marks the conversation complete anyway. On completion the agent distils the whole conversation into a one-sentence situation. The frontend shows a Start plan card, and when the user presses it, sends the situation and collected facts to the planner as a new job. The agents don't call each other: each turn and the plan are separate jobs through the Api, Worker and DynamoDB, as on the next slide. Both agents call Claude on Bedrock and query the service graph through AgentCore Gateway: the conversation agent to work out what to ask, the planner to build the steps.

## [diagram] Agents answer through a job queue, not directly
The frontend never calls an agent. It starts a job and polls until the Worker saves the agent's reply.

![The user's browser talks to the Next.js frontend on Amplify. The frontend starts jobs and polls the Api Lambda, which saves each job in a DynamoDB table and starts the Worker Lambda. The Worker calls the conversation or planner agent on AgentCore Runtime and saves the reply to the job. The agents call Claude on Bedrock and use the service graph MCP server through AgentCore Gateway.](diagrams/containers.svg)

Notes: Frontend: Next.js 16 server actions call the Api Lambda (start_chat, start_plan, get_job). Api: saves a pending job in the DynamoDB jobs table and invokes the Worker asynchronously. Worker: calls the agent runtime and writes the reply back to the job; MAX_WORKERS caps concurrency. Agents: two Python runtimes on Bedrock AgentCore in eu-west-2. The conversation agent gathers facts one question at a time until it has enough; the planner turns them into a step-by-step plan. Both query the UK government services graph, an MCP server running as a Lambda behind AgentCore Gateway. Evaluation scripts and observability are left out.

## [diagram] Each container is a few small components
The same containers as the last slide, opened up to show their main parts.

![Inside the frontend, pages and a poller in the browser call server actions, which use a backend client to invoke the Api Lambda. In the backend, the Api handler saves and reads jobs through the job store in DynamoDB and starts the Worker handler, which claims the job, invokes the agent and saves the reply. On AgentCore Runtime, each agent's entry point passes the request to its chat or plan logic and then to an agent runner, which calls Claude on Bedrock and the service graph's MCP tools through Gateway. The tools use a graph engine over the rules and data.](diagrams/components.svg)

Notes: Frontend: pages and the poller are app/page.tsx, app/components and lib/poll.ts, with the session kept in the browser's sessionStorage (lib/storage.ts). Server actions are app/actions.ts and the job route app/api/job/route.ts. The backend client is lib/ask-backend.ts and lib/backend.ts. Backend: the Api handler is src/api-handler.ts and api.ts, which starts jobs (start.ts) and looks them up for polling (look-up.ts); the Worker handler is src/worker-handler.ts, worker.ts and run-job.ts: it claims the job so only one run takes it, invokes AgentCore through src/agents.ts, and saves the result or marks the job failed; the job store is src/store.ts over the DynamoDB jobs table. Agents: each runtime has a BedrockAgentCoreApp entry point (main.py), its logic (chat_logic.py, which applies the five-question cap and asks for the situation summary, or planner_logic.py, which builds the prompt from the situation and facts) and a Strands agent runner (chat_agent.py or planner_agent.py) with its system prompt. Common code is in agent/shared. Service graph: lambda-handler.ts runs graph-server.ts, which exposes five MCP tools, over graph-engine.ts, graph-data.ts and rules.ts. The agents reach the tools at GRAPH_GATEWAY_URL; locally they run graph-server.ts over stdio instead.

## [diagram] Proposed: two frontends share one public API
When the user presses Start plan, the chat orchestrator hands the context to the plans backend. Navy marks what is new.

![Proposed: users reach the service through the web frontend or a new GOV.UK app in React Native. Both call a new public API, which checks the user's token with an identity provider. The API routes to two separate parts. A Chat V2 agent or orchestrator holds the conversation agent; how it is built is to be confirmed. When the user presses Start plan, it sends the context to a new generate plan endpoint. The plans backend also has a new get plans endpoint, a plan worker and a new plan store kept by user, and calls the planner agent. Both agents call Claude on Bedrock, and reach the service graph through AgentCore Gateway.](diagrams/proposed.svg)

Notes: A proposal, not the current build. Frontends: the existing Next.js web frontend and a new React Native GOV.UK app. The app can't use Next.js server actions, so both call one public API, shown as API Gateway in front of the backend Lambdas. Identity is generic: an identity provider signs users in, and the API checks the user's token, so plans can be kept and fetched per user. Chat V2 agent/orchestrator: holds the conversation agent, separate from the plans backend. Its backend design is to be confirmed, so the slide shows only the agent. Handoff: when the conversation agent judges it has enough, the user is shown the facts and a Start plan button. Pressing it tells the orchestrator, which calls generate plan itself with the user's identity, the situation summary and the structured facts, against an agreed, versioned schema. The client never carries the facts, and the transcript stays in Chat V2. Plans backend: generate plan is called by the orchestrator, not the client. It saves a pending plan for the user, with the context it was given, and starts the plan worker, which calls the planner agent and saves the finished plan. The frontend polls get plans until it is ready, and later uses get plans to show the user's saved plans. The plan store's technology is left open. The planner agent stays on AgentCore Runtime. Both agents call Claude on Bedrock and reach the service graph's MCP tools through AgentCore Gateway, as today.
