    Why we need this

    A personalised plan can go wrong in two ways

    It is wrong for this person

    It tells someone to apply for a licence they already hold, or adds a step that has nothing to do with them.

    Measured by relevance

    It changes every time

    Ask twice and get two plans, with a different number of steps or a different fee for the same service. People can't act on a plan they can't rely on.

    Measured by consistency

    Reading plans by hand doesn't scale. Every change to the planner's prompt, model or tools needs checking again, across many kinds of user. So the checks run as code, an AI judge makes the calls that need judgement, and every call is saved with its reason.

    The process · stages 2 to 4

    Synthetic users come from the guidance itself

    • The content decides the questions. Claude reads the guidance and proposes only questions where the answer changes what a person must do, each citing the page that justifies it. The driving questionnaire has 15 questions and 21 derived facts.
    • Code checks the questionnaire. Thousands of invented answer sets test that every question can be reached, every answer can occur and every rule does something. Faults go back to Claude for up to three rounds, then a person reviews it.
    • Code builds the users. It walks the questionnaire 20,000 times and keeps one profile per distinct set of answers: 90 for driving, with every answer used at least once.
    • Nobody impossible. Age isn't asked, so it is worked out from the answers. Someone who passed a test before 1997 can't be 19.
    • Nothing in the code is about driving. The same scripts have produced a questionnaire for having a baby.

    Generate and score

    Generate plans once, then score them as often as you like

    Generate

    python -m metrics.harness generate

    Asks the hosted planner for G plans per profile, the way the backend does: the situation, answer codes, age and today's date, in a fresh session each time.

    Each call can take minutes. The file is saved after every profile, and throttling or timeouts are retried.

    This run: 9 profiles × G = 3 → 27 plans

    plans file

    Score

    python -m metrics.harness score

    Runs each judge N times over the saved plans and writes results.json.

    Judging is quick, so the same plans can be scored again after any change to a judge prompt.

    This run: N = 2 → 164 judge calls

    results.json

    Dashboard

    python dashboard.py

    One HTML page per folder of results.

    The planner's model and the judge's model are set separately (ANTHROPIC_MODEL and EVAL_ANTHROPIC_MODEL), with no fallback between them. In this run the judge was Claude Sonnet 5.5 on Bedrock.

    Relevance

    Relevance asks whether each task belongs in this person's plan

    The judge sees

    • The situation, in the person's own words
    • Their answers as codes, their age and today's date
    • Each task's title, summary, GOV.UK service and link

    The judge doesn't see

    • The planner's own reasoning
    • Any answer key or published step by step
    • Each step's status, such as Done. This turns out to matter.

    The judge decides in this order

    1. 1

      Does the task's subject serve the situation at all?if not

      Irrelevant
    2. 2

      Does one of their answers rule it out? Already done, not eligible, or a different vehicle.if so

      Contradicted
    3. 3

      Otherwise the task is needed, now or later in the journey.then

      Relevant

    Plan score = relevant tasks ÷ judged tasks. Each plan is judged N times and averaged, then a person's plans are averaged.

    Service stability

    code, no judge

    Do the plans recommend the same GOV.UK services? The overlap of their service links, for each pair of plans, averaged.

    B

    Fact consistency

    judge, one call per shared service

    Where plans share a service, do they contradict each other about it? Cost, department, deadline, requirements, how to apply. Extra detail or different wording doesn't count.

    C

    Structure consistency

    judge, one call per pair of plans

    Same number of steps, covering the same things in the same order, with summaries describing the same route? A pair counts as the same only if the judge finds no differences.

    Consistency · A · worked example

    Service stability: which services each plan recommends

    With three or four services per plan, one extra service moves a pair's score by about 0.25, so treat small differences between runs as noise.

    Consistency · B · worked example

    Fact consistency: do the plans agree about a shared service?

    The judge made 56 checks in this run and found contradictions in 5. They come from the three cases below.

    Not counted as a contradiction

    • One plan gives detail the other leaves out
    • The same fact in different words
    • A vague claim beside a compatible specific one, such as "soon" and "within 5 days"

    Consistency · C · worked example

    Structure consistency: two plans side by side

    Each pair is shown to the judge in a random order, fixed by a seed so reruns match. Over many pairs, any lean towards the plan shown first cancels out.

    Trusting the judge

    How the judge is kept honest

    Reason first

    The judge writes one sentence naming the answer it relied on, then gives its verdict.

    Examples from elsewhere

    Relevance and structure examples are about a bereavement, and fact examples use a different service, so they show the rules without giving answers away.

    Answers read literally

    A missing answer counts as unknown, never as "no".

    Plans are data

    The person and the plans are wrapped in tags marked as data, so text inside a plan can't give the judge instructions.

    Order shuffled

    Pairs of plans appear in a seeded random order, which cancels out any lean towards the first plan.

    Judged more than once

    Every judgement runs N times. Scores report the lowest and highest run.

    Failures stay visible

    A failed or unreadable reply is retried twice, then marked unjudged and left out of the score. This run: 3 of 172 tasks.

    Bad credentials stop the run

    Access denied or an expired login ends scoring at once, rather than filling the results with unjudged items.

    Weighting

    Weighting counts common learners more than rare ones

    The 90 profiles cover every route once, so a rare route counts as much as a common one. weights.py gives each profile a weight so that each answer's share matches real users. It rescales one question at a time and repeats until nothing moves.

    Most of the lost relevance comes from steps the planner had already marked Done

    Judge's verdicts by step status

    172 task judgements: 27 plans, each judged twice

    Example: P085, plan 1

    DoneHold a provisional driving licence

    Task: "Apply for a provisional driving licence", £34

    The planner usually keeps completed steps in the plan and marks them Done. The judge is never shown a step's status, so it reads the task as advice to apply again and calls it contradicted.

    All 35 contradicted verdicts were on Done steps. When a done step was worded as upkeep, such as "Keep your theory certificate ready", the judge called it relevant instead (12 times). The verdict depends on wording the planner chose.

    Results · reading the evidence

    What else the evidence shows

    8 of 27 plans

    Vehicle tax comes and goes

    "Tax your vehicle" appeared in 8 plans, and in all three plans for only one learner. The judge called it irrelevant all 16 times, since nothing says the learner owns a car. It accounts for 4 of the 6 services that appear in some of a learner's plans but not others.

    £23 or £0

    Fees on completed steps change between plans

    A theory test already passed cost £23 in one plan and £0 in the other two (P018). A provisional licence already held cost £34 in one plan and £0 in two (P057). The judge flagged both in both of its runs.

    1 of 2 runs

    One rule contradiction, caught once

    For P045, one plan said a pass lapses if you don't hand your provisional licence to the examiner. The others said you can still claim the full licence with form D1. The judge flagged it in one of its two runs, which is why each check runs more than once.

    22 of 54 pairs

    Plan shape varies most

    Only 22 of 54 pair judgements found the same structure. Steps appear and disappear (tax, completed steps) and summaries mention different things. Services (0.88) and facts (0.91) were far more stable.

    Results

    How far to trust these numbers

    A small, lopsided sample

    9 learners with an effective sample size of 3.1. Treat the weighted scores as provisional.

    Some profiles can't exist

    P018 and P069 have passed the theory test without a provisional licence, which isn't possible in Great Britain. Together they hold 4.9% of the weight.

    Three plans per person is few

    One extra service moves a pair's overlap by about 0.25.

    The judge reacts to wording

    The same completed step was called contradicted or relevant depending on how the planner phrased it.

    Some weights are assumptions

    There is no public source for accessibility or PIP shares among learner drivers, and the stage shares use test volumes as a stand-in.

    Faithfulness isn't measured

    Checking a plan against what the knowledge graph returned needs the planner's tool results, and the hosted planner doesn't return them.

    Using it

    Running it and reading the results

    # from scripts/evaluation/plan-generation
python weights.py data/profiles/driving_profiles_v5.json data/weights/driving_weights_v2.json \
    -o data/profiles/driving_profiles_v5_w2.json
python -m metrics.harness generate data/profiles/driving_profiles_v5_w2.json -G 3 -o data/plans.json
python -m metrics.harness score data/plans.json -N 2 --results-out data/results/results_w2.json
python dashboard.py            # writes data/results/dashboard.html

    What each step needs

    • generate: AGENT_RUNTIME_ARN and permission to invoke the hosted planner
    • score: EVAL_ANTHROPIC_MODEL and Bedrock access for the judge
    • dashboard.py: only Python, works offline

    The dashboard shows

    • Each run's settings, with warnings for skipped profiles and unjudged items
    • Mean and weighted mean for every measure, and the lowest-scoring learner
    • Every verdict, contradiction and structure difference, with the judge's reasons
    • Any one learner's answers, plans and verdicts

    Plans files record the runtime ARN, which includes the AWS account ID. Results files and the dashboard never do, but they contain local file paths, so check them before sharing.

    Open questions and next steps

    Decisions this run raises

    • Should a plan show steps the person has already done? If so, show the judge each step's status, or leave Done steps out of relevance.
    • Should a completed step show its fee or £0? Either works, as long as plans agree.
    • Should learners see vehicle tax? Decide, then tell the planner.

    From the weighting review

    • Regenerate the car profiles with realistic combinations, so nobody has a theory pass without a provisional licence.
    • Weight by age too, or create several personas per answer set across age bands.
    • Replace the stand-in shares with GOV.UK analytics or a learner survey.
    • Report how much the scores move under different accessibility and PIP shares.

    Not built yet

    • Faithfulness, which needs the planner to return its knowledge-graph results.
